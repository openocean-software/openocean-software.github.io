    Toolkit

    The build pipeline, the signed apt repositories and the public plan. All of it is open source under the openocean-software GitHub organization.

    Packages

    Member projects keep a working build (CMake, pyproject.toml, etc.) and a tagged release schedule. The openocean-build pipeline builds, signs, and publishes the packages to apt.oceansoft.org. Its documentation is at build.oceansoft.org, including a getting started guide for member projects.

    Member project

    git, a working build, signed release tags

    →

    Open Ocean pipeline

    sbuild in Docker, install test, GPG signing

    Channels

    Packages are published to three channels, each its own set of apt repositories:

    Channel Contents Signed with Projects
    Release Tagged releases, published after a reviewer approves Release key MOOS-IvP, Goby3, DCCL, NETSIM
    Beta Tagged prereleases Release key openocean-messages
    Continuous The latest trusted commit on each project's main branch Continuous key Goby3, DCCL, NETSIM, IvPico, the IvP Helm libraries without MOOS, openocean-messages

    The release channel also carries the dependencies these projects need that Debian and Ubuntu don't package (MAVLink, libais, Wt).

    Install from apt.oceansoft.org

    Trust

    These instructions assume oceansoft.org and the openocean-build repository haven't been compromised (and thus list the correct GPG fingerprints). This is normally a safe assumption, but if your security requirements call for it, consider independently verifying our signing key, e.g. using Keybase or other out-of-band techniques.

    For Debian bookworm and trixie, and Ubuntu jammy, noble and resolute, on amd64 and arm64. A few projects skip a release whose dependencies are too old.

    apt-setup adds the release channel, checking the key's fingerprint before apt is told to trust it:

    curl -fsSLO https://raw.githubusercontent.com/openocean-software/openocean-build/main/scripts/apt-setup

    sudo bash apt-setup

    Options add more: --beta and --continuous for those channels, and --zenoh for Eclipse Zenoh's repository, which goby3-zenoh needs.

    • Get the release key and check its fingerprint (details): 
      OOS_KEY=D7D7224D53A4F29E303FE01DEB505B68A5D063B0
OOS_KEYRING=/usr/share/keyrings/openocean-release.asc
curl -fsSLO https://raw.githubusercontent.com/openocean-software/openocean-build/main/keys/release.asc
gpg --show-keys --with-colons release.asc | grep -x "fpr:::::::::$OOS_KEY:" && sudo install -m 0644 release.asc $OOS_KEYRING
    • Add apt sources: 
      DISTRO=$(. /etc/os-release; echo "$ID")             # "ubuntu" or "debian"
DIST=$(. /etc/os-release; echo "$VERSION_CODENAME") # e.g., "resolute"
printf 'Types: deb\nURIs: https://apt.oceansoft.org/release/%s-%s\nSuites: %s\nComponents: main\nSigned-By: %s\n' \
  $DISTRO $DIST $DIST $OOS_KEYRING | sudo tee /etc/apt/sources.list.d/openocean-release.sources
sudo apt update

    The beta channel is the same with beta in place of release in the URL. The continuous channel also needs its own key. See Installing packages.

    Then:

    • Install packages: 

      sudo apt install ...

    • Full list of packages available: 

      sudo apt install lz4
lz4cat /var/lib/apt/lists/apt.oceansoft.org*_Packages.lz4 | grep '^Package:'

    Set up before November 2026?

    The repositories moved from apt.oceansoft.org/<distro>-<dist>/ to apt.oceansoft.org/release/<distro>-<dist>. Remove /etc/apt/sources.list.d/oceansoft.list and /etc/apt/keyrings/oceansoft.gpg, then follow the steps above.

    Roadmap

    The plan is public in openocean-plan. The technical goals come from 114 interviews with people in academia, industry and government, described in the AUV26 paper. Comment on any of them on the forum.

    Goal Status What it gives member projects
    Middleware interoperability In progress Common message set and maintained bridges
    Linux packages In progress Shared, signed apt repositories: release, beta and continuous
    Continuous integration Planned Shared CI templates and maturity badges
    Embedded builds Planned Raspberry Pi and ARM builds in CI
    Docker images Planned Dockerfile templates and multi-arch images
    Data QA/QC and FAIR data Planned QC checklists, metadata templates, provenance
